Механизм проверки при каждом preflight сверяет SHA исходного DOCX и матрицы, fingerprint структуры и действительное содержание узлов. Для RF013 дополнительно сверяются оба диагностических DOCX и присутствие всех девяти абзацев. Статусы отдельно аудитируются в `TemplateAuditEvent` и не трактуются как выполненный `DELETE` или фиктивный `DocumentBinding`. Это ограничение именно для RF011/RF012 (`template_scope=NONE`) и RF013 ИП (`required=YES`, `INCLUDE`). Для RF004/RF017 проверяются ID, поле, диапазон и активность каждой реальной `DocumentBinding`; добавлено одно обязательное поле ФИО на вариант. Точечное формирование обеих преамбул в временном DOCX проверено. Для RF002 проверяются условный абзац, точечная привязка и формат LIST; на обоих вариантах в временных DOCX проверены пустой список и два приложения вместе с соседними абзацами.

## Точные технические остатки

- В `QuestionnaireSchema` шаблонов теперь есть общее поле ФИО и его привязки, но пока нет типизированных источников `price.total`, `tax.ndfl_rate`, `tax.ndfl_amount`, `tax.vat_rate`, `tax.vat_amount`, `tax.no_vat_basis` и структурированных дат договора. Одной сменой статуса RF006/RF009/RF018/RF019 их не заменить. Нужно добавить поля и детерминированные выражения, затем проверить реальные привязки к каждому диапазону.
- RF002 теперь использует существующий `LIST` с детерминированной нумерацией, точечную привязку и `ConditionalDocumentRegion`; контрольные временные DOCX подтвердили отсутствие изменений соседних абзацев.
- Для RF016 нет структурированных дат **действия договора** и двух проверяемых email-источников для `xxx`; даты оказания услуг `term.start/end` нельзя без согласованного правила молча считать датами действия договора.
- Для RF018/RF019 требуется отдельная стоимость конкретного акта и серверный контроль суммы нескольких актов с округлением налога. Текущий `DocumentDraft` содержит один набор ответов и не ведёт реестр актов одного договора. Без этой связи нельзя честно проверить совокупный лимит и соответствие НДФЛ.
- RF024 хранится как `COMPOSITE`, но пока только из двух текстовых компонентов («Паспортные данные» и «СНИЛС»). Требуются пять валидируемых компонентов и точечные привязки внутри исходной ячейки.
- Продукт `TRAINING_CONTRACT` и его версия остаются `DRAFT`; у версии есть два варианта, но пользовательская цепочка `QuestionnaireSchema → TemplateVersion → ContractProductVersion` ещё не принималась сквозным тестом. Доступ обычным пользователям открывать рано.
