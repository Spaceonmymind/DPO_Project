Критический порядок решений: проверить заказчика, предмет, возмездность, статус исполнителя, гражданство/возраст, личное оказание и трудовые признаки; затем выбрать `PHYSICAL_PERSON` или `INDIVIDUAL_ENTREPRENEUR`; только после этого проверять полноту применимых RF. НПД имеет приоритет над ИП и блокирует оба текущих варианта. Неизвестные или противоречивые критические факты дают `NEEDS_INPUT`, запрещающие условия — `BLOCKED`, а `READY` допустим только при отсутствии пропусков и полном покрытии применимых вхождений.

## Самые рискованные OOXML-фрагменты

1. **Графики в таблицах 1 и 6.** RF021 имеет 36 вхождений, но бизнес-сущность — массив строк, а не 36 независимых строковых замен. Нужны клонирование строк, пересчёт итогов и проверка структуры таблицы.
2. **Условная колонка RF020.** Безопасное удаление колонки требует менять grid, cells и spans согласованно; простая замена текста оставит пустую колонку или повредит layout.
3. **Оплата RF007/RF008.** Выбор одного из трёх многоабзацных блоков плюс условная банковская гарантия не выражается single-node locator.
4. **Юридические блоки RF011–RF016.** Удаление или включение целых абзацев должно сохранять нумерацию, ссылки и соседнее форматирование.
5. **237/240 маркеров Word fields.** Любая ошибочная привязка к `fldChar/instrText` отвергается renderer; однако preview не помечает такие зоны заранее.
6. **Повторяющийся текст.** Структурный путь различает одинаковые тексты только внутри immutable version. После загрузки новой версии требуется явный rebase, а не перенос offsets по совпадению текста.
7. **Суммы и налоги.** Несогласованность цифр, суммы прописью, НДФЛ/НДС и актов создаёт юридический риск; генерация должна fail closed.

## Единый договорный продукт

Предлагается добавить над `DocumentTemplate` конфигурационную сущность `ContractProduct` с кодом `TRAINING_SERVICES`, общей `QuestionnaireDefinition` и набором `ProductVariant`:

```text
ContractProduct
  ├─ shared questionnaire/fact schema
  ├─ declarative applicability ruleset (versioned, published, immutable)
  └─ ProductVariant
       ├─ PHYSICAL_PERSON -> pinned TemplateVersion
       └─ INDIVIDUAL_ENTREPRENEUR -> pinned TemplateVersion
```

`ProductVariant` хранит `variant_key`, `template_version_id`, `priority`, декларативное условие и статус. Draft сначала pin-ит опубликованные product/rules/schema versions, собирает общие факты, получает детерминированный `ApplicabilityDecision`, затем pin-ит ровно один `TemplateVersion` и показывает вариантные вопросы. Правила исполняются только allowlisted интерпретатором выражений; произвольный Python/JS запрещён. При `BLOCKED`, `NEEDS_INPUT`, неоднозначности или неполном покрытии render не запускается.

Отдельные Python-ветки для физлица и ИП не нужны: различаются данные варианта, bindings и декларативные правила.

## Изменения structural locator/API

Текущий locator v1 следует сохранить для simple range. Для Stage 3 необходим versioned union:

- `TEXT_RANGE`: существующий part/node/start/end + fingerprint;
- `PARAGRAPH_BLOCK`: start/end paragraph paths, expected hashes и container;
- `TABLE`: table path + table fingerprint;
- `TABLE_ROW_TEMPLATE`: table path, row identity/index, cell schema, row hash;
- `TABLE_COLUMN`: table path, grid column, затрагиваемые cell paths и span policy;
- `PART_RANGE`: отдельный part для header/footer/footnote; headers/footers уже читаются, footnotes пока нет.

API выбора должно возвращать `operation`, `locator_kind`, `expected_structure`, `supported=true/false` и понятную причину. Нельзя создавать фиктивную binding, если выбранный диапазон пересекает параграфы или не может быть безопасно воспроизведён. Renderer перед каждой операцией проверяет fingerprint, текст/структуру, отсутствие конфликтов и постусловия DOCX.

## Blockers и открытые вопросы

- Матрица утверждает 74 вхождения исходного DOCX, но использует единую систему `P…/T…`, тогда как два утверждённых варианта уже содержат вариантно-специфичный текст. Перед импортом нужен машинный reconciliation каждого occurrence с каждым конкретным DOCX locator v2.
- FACT_SCHEMA содержит факты, не представленные среди RF001–RF025 (например, сроки, цена как число, строки графика), а реальные DOCX содержат дополнительные незаполненные placeholders вне красной карты. Нужно юридически подтвердить границу автоматизируемых полей.
- Нужно утвердить: кто задаёт общие данные заказчика/подписанта/реквизиты; допустима ли генерация частично заполненного ТЗ; какие правила округления налогов и словесной суммы применяются.
- Нужно определить семантику двух графиков: оба формируются из одного массива или являются независимыми наборами.
- Нужна юридическая приемка операций удаления блоков и колонки на эталонных generated DOCX.

До закрытия этих вопросов оба договора пригодны как regression fixtures, но не как автоматически публикуемый продукт.
