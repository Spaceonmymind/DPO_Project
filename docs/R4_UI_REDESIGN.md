# R4.0 — переработка UX/UI платформы договоров

## Результат аудита

До R4 интерфейс объединял два разных продукта: legacy-сценарии обращений/ТЗ и новую платформу договоров. Главная страница, основная кнопка и навигация вели в AI-dialogue, а каталог договоров одновременно показывал шаблоны, черновики и анкету. Конструктор находился в узкой вложенной сетке; технические действия отображались возле каждого DOCX-узла постоянно и создавали визуальный шум.

Backend-платформа договоров при этом уже разделена на шаблоны и закреплённые версии, схемы анкет, структурные привязки, условные области, повторяемые группы, черновики пользователя и сформированные документы. R4 сохраняет эти API и модель данных: переработан маршрут пользователя, а legacy API и данные не удалены.

## Новая информационная архитектура

- `/` — договорная главная: создание документа, реальные метрики и незавершённые анкеты.
- `/contracts` — каталог только опубликованных и доступных шаблонов; после выбора открывается анкета.
- `/documents` — личные черновики и сформированные документы.
- `/templates` — конструктор для `dpo_specialist` и `administrator`. Для обычного пользователя маршрут закрыт также на уровне интерфейса; backend остаётся источником истины для авторизации.
- Legacy-маршруты сохранены для обратной совместимости, но исключены из основной навигации и главной страницы.

Анкета состоит из этапов «Анкета» и «Проверка», показывает прогресс по активным полям и сохраняет ответы автоматически. Переход к формированию не выдаёт визуальный preview за готовый DOCX: пользователь проверяет структурированную сводку, а затем скачивает сформированный файл.

## Рабочее пространство конструктора

После выбора шаблона каталог освобождает экран под редактор. Рабочий процесс представлен шестью понятными этапами:

1. Общие сведения.
2. Исходный документ.
3. Поля и привязки.
4. Анкета.
5. Условия и повторяемые таблицы.
6. Проверка и публикация.

Центральная область построена как трёхпанельное пространство: структура и поиск слева, документ в центре, контекстные настройки текущего этапа справа. На меньшей ширине outline скрывается первым. Действия структурного узла появляются при наведении или клавиатурном фокусе, поэтому сам договор остаётся читаемым. Все существующие операции R3.1–R3.4 остаются доступны, а переключение этапов не размонтирует редактор и не теряет локальное состояние.

## Feasibility DOCX-preview

Рассмотрены три реалистичных подхода.

| Подход | Визуальная точность | Связь с OOXML | Вывод |
|---|---:|---:|---|
| Клиентский HTML-рендерер (`docx-preview` и аналоги) | Выше текущей, но не идентична Word | Нестабильная: DOM не является исходным деревом OOXML | Возможен как дополнительный read-only слой |
| Серверная конвертация DOCX → PDF/HTML | Хорошая при наличии LibreOffice/MS Office | Координаты/HTML не дают надёжный структурный locator | Подходит для финального просмотра, не для привязок |
| Структурный OOXML-preview через `DocumentEditorAdapter` | Упрощённая типографика | Надёжная привязка к paragraph/table-cell locator и fingerprint | Выбран для конструктора |

В R4 сохранён структурный adapter: он показывает текстовые узлы, таблицы, выделения и связанные области, но не заявляет точную пагинацию Word. Split runs нормализуются на уровне структурного текста; таблицы сохраняют locator ячейки; одинаковый текст различается по структурному пути и fingerprint. Headers/footers и сложная геометрия Word не отображаются как полноценная страница, а merged cells зависят от возможностей текущего OOXML parser. Координаты HTML/PDF не используются как идентификатор.

Для следующего этапа рекомендуются два слоя: структурный режим для настройки bindings и отдельный fidelity-preview сформированного документа. ONLYOFFICE может быть подключён через существующую границу `DocumentEditorAdapter`, но его внедрение и сервер документов не входят в R4.

## Что не менялось

R4 не меняет schema/API R3, вычисления, condition engine, renderer и immutable-оригиналы DOCX. Новая миграция БД не требуется. Legacy-код и существующие данные не удалялись.
